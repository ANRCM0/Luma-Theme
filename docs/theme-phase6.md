# vv-theme 第六阶段：订单与支付闭环（v0.8.0）

## 改动范围

本阶段**仅调整主题的订单操作与支付状态展示**。TXBoard 仍是订单、支付金额、订单锁及回调的唯一权威数据源，不改后端订单服务或支付网关。

### 1. 待支付订单恢复

用户提交新订单时，先调用 `/api/v1/user/order/fetch`，查找状态为 0（待支付）或 1（开通中）的已有订单：

- **状态 0：** 优先提供“继续支付原订单”。若用户明确选择“取消原订单并重新下单”，才弹确认框，重新检查原订单状态，调用服务端取消接口，再检查是否有别的进行中订单，最后提交新订单。
- **状态 1：** 只允许查看原订单处理进度，不允许取消、再次支付或创建新订单。
- **状态 2、3、4：** 是终结状态，不阻止用户按服务器规则购买新套餐。
- 若用户取消确认或旧订单状态变化，主题不会默默取消订单、更不会在后台自动重新扣款。

服务器 `OrderService` 本身存在订单冲突校验与事务锁；本阶段保留该最终兜底。

### 2. 支付状态自动查询

调用 TXBoard 已有 **`GET /api/v1/user/order/check?trade_no=...`**，只查询订单状态，不读取支付卡信息、不重复调用 checkout，也不猜测支付成功：

- 只有用户打开订单详情、状态仍为 0/1 且已登录时开始；默认每 4 秒检查一次。
- 浏览器标签页隐藏时跳过请求；关闭订单弹窗或用户退出登录时停止。
- 每次订单详情最多尝试 20 次（默认约 80 秒），超时提示用户手动刷新。
- 状态变化时通过 `/api/v1/user/order/detail` 获取权威详情；订单进入已取消/完成/已折抵时刷新用户与订单数据。
- 状态未知、响应超时或网络断线不会被当作支付失败；不会替用户执行再次支付。

### 3. 支付失败与浏览器拦截

- 点击“立即支付”后同步加防重锁并禁用按钮，防止同一页面内连续点击重复发起 checkout。
- 在支付前再次向服务器查询订单状态。状态已改变时，展示新状态，而不是重复付款。
- 支付网关调用失败时保留当前订单、支付方法和错误提示，允许用户**手动**重试。
- 第三方支付 URL 必须通过原有 `safeExternal` 校验。弹窗被拦截时展示可点击的 HTTPS 手动支付链接。
- Stripe 信用卡支付继续委托 TXBoard 原生安全组件。
- 实际应付金额以 `order/detail` 返回为准；展示的手续费为估算，不参与订单计价。

## 主题配置

「主题管理 → vv-theme → 设置 → 订单与支付」：

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `payment_auto_check` | 1 | 自动查询后台订单状态，不会发起支付 |
| `payment_poll_seconds` | 4 | 轮询间隔，限制在 4 至 15 秒；最多尝试 20 次 |

关闭自动查询后仍可点击“刷新订单状态”手动检查。

## Node.js 22 单一 CI

前端工作流从 `matrix: ['20','22']` 变成单个 Node.js 22 作业。以下任务仍全部保留：

1. `npm test` 单元与协议测试
2. `npm run build` 普通前端构建
3. Playwright 演示模式浏览器端到端测试
4. TXBoard 真实主题模式打包构建
5. Playwright 模拟后端 API 浏览器回归

主题打包及 GitHub Pages 原本就采用 Node.js 22，无需再建重复矩阵。

## 预发环境验收重点

- 存在旧待支付订单：优先继续支付，任何取消均需明确用户确认。
- 存在开通中订单：不能创建或支付新订单。
- 真实网关响应缓慢：单次点击只生成一次支付请求，失败提示可重试。
- 第三方收银台弹窗被浏览器拦截：手动支付链接可用。
- 支付异步通知延迟：后台状态实际变更后主题才显示完成，且停止查询。
- 用户关闭订单、退出登录或自动查询达到上限时，不应产生额外支付或无限状态请求。
- 真实 Stripe、安全重定向、手续费计算及网关回调应在预发布账户上测试；CI 只验证模拟 API。

前五阶段功能保持不变。正式环境的实际支付回调不由 GitHub Actions 验证。
