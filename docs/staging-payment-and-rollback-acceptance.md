# Luma Theme — staging payment/callback and rollback acceptance

Tracking: #13. **Status: NOT RUN on a real staging TXBoard. NO-GO until evidence is recorded.** The read-only preflight script is not a payment test. Refer to the backend guide at [TXBoard staging release acceptance](https://github.com/ANRCM0/TXBoard/blob/main/docs/operations/release-staging-acceptance.md).

## Guardrails and prerequisites

- Dedicated staging hostname (HTTPS), fresh isolated MySQL 8.4/Redis and TXBoard deployment pinned by immutable image digest. Never aim this procedure at live users or databases.
- A verified off-host backup and a tested restore for the staging stack including APP_KEY and installed theme files.
- A sandbox merchant/account that can produce actual signed provider callbacks. Never simulate a valid provider receipt by directly editing DB balances or POSTing a fabricated success to a real merchant callback.
- Staging-only administrator, ordinary user, reversible test plan, coupon, staging domain and callback endpoint.
- Use only sandbox funds and explicitly authorized operator test transactions. Never insert payment credentials, bearer tokens, APP_KEY or subscription URLs in PRs, CI artifacts or issue comments.

## Step 1 — Verify tagged release ZIP and public staging

Download a candidate tagged GitHub release artifact and its adjacent SHA256 file from the same release. Avoid the autogenerated source ZIP.

```sh
node scripts/staging-theme-preflight.mjs \
  ./luma-theme.zip ./luma-theme.zip.sha256 \
  https://staging.example.test TXBoard
```

This **read-only** script validates ZIP checksum, manifest `vv-theme`, Blade and hashed assets; checks GET /txapi/health, public site-config and default-root HTML. It rejects URLs not explicitly labeled staging/test/dev, plain remote HTTP and embedded credentials. No login or data modification.

Install the verified ZIP in staging, enable `vv-theme` from its administration UI, and rerun:

```sh
node scripts/staging-theme-preflight.mjs \
  ./luma-theme.zip ./luma-theme.zip.sha256 \
  https://staging.example.test vv-theme
```

It checks public site-config and loads Luma CSS/JS at the actual install path. A PASS here only means publicly accessible assets/entrypoints, not successful login or payment.

## Step 2 — Staging business and payment acceptance (operator in browser)

Record each step as **PASS**, **FAIL**, **BLOCKED** or **NOT_RUN** with sanitized timestamps and transaction IDs.

| Case | Actual sandbox/backend evidence required |
| --- | --- |
| Authentication | Register, login, logout, expired token; stale session rejected |
| Purchase | Server-provided plan price; coupon; initial unpaid order; resume and explicit cancellation |
| Checkout | QR and redirect; Stripe only when configured, with real provider test keys |
| Provider callback | Signed sandbox payment causes one status transition and correct plan/subscription/traffic read-back |
| Callback retry / loss | Duplicate valid callback settles only once; deferred callback can be recovered; forged signature and altered amount rejected |
| Wallet recharge | No credit before callback; one credit after valid callback; duplicate callback no further credit |
| Failure recovery | Unavailable payment gateway; no repeat order creation; manual status refresh after polling cap |
| User experience | Mobile 320/375/390 and desktop layouts, dark/light, purchase/order/ticket dialogs |
| Theme rollback | Switch admin setting to default TXBoard; root no longer loads Luma assets; users and wallet balances unchanged |

After switching the theme to `TXBoard`, run the same preflight with the `TXBoard` expected mode again. **Do not** delete the Luma theme folder to mimic rollback.
